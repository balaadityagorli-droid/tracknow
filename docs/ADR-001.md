# ADR-001: TrackNow Architecture Decision Record

**Status:** Accepted  
**Date:** 2026-11  
**Team:** PS08 Hackathon

---

## Context

Build a live delivery tracking platform (TrackNow) for 2,000+ concurrent riders and thousands of simultaneous viewers. Requirements: sub-2-second map delay, zero polling, zero double assignment, exactly-once notifications, graceful Redis failure handling, and client failover within 5 seconds.

---

## Decision 1: Redis as the Real-Time Coordination Layer

**Chosen:** Redis for location, assignment locks, pub/sub fan-out, and rate limiting. SQLite WAL is the persistent source of truth for all orders.

**Rationale:**
- GEOSEARCH enables nearest-rider lookup in < 1 ms (well under 50 ms p95)
- Pub/Sub fan-out without polling — zero HTTP polling requests by design
- EVALSHA Lua scripts provide atomic check-and-write (prevents double assignment across instances)
- Redis can be interrupted without data loss (SQLite holds all order state)

**Rejected alternatives:**
- Database polling: would create write saturation and O(N) polling storms
- Server-Sent Events: unidirectional, can't report latency back
- Long-polling: adds 1–2 s latency by definition

---

## Decision 2: Custom Lua Scripts for Atomicity (not library locks)

**Chosen:** Three Lua scripts loaded via SCRIPT LOAD / EVALSHA:
- `update_location.lua`: rate-limit + stale-seq check + GEOADD in one atomic operation
- `claim.lua`: GEOSEARCH candidate → check rider status + set all assign-guards + update rider hash atomically
- `release.lua`: clear guards + re-add to available pool

**Rationale:** Redis Lua scripts run atomically without MULTI/EXEC overhead. No lock library needed. The team can explain and defend every line.

**Dev fallback:** Pure-JS emulation in `dev/miniredis.js` mirrors exact script logic for Windows dev without a Lua binary.

---

## Decision 3: Transactional Outbox for Exactly-Once Notifications

**Chosen:** SQLite `outbox` table + `notifications` table. Worker polls every 150 ms. `INSERT OR IGNORE INTO notifications` (PK on `order_id, version`) makes the effect idempotent.

**Rationale:**
- Notification delivery and outbox mark happen in one `BEGIN IMMEDIATE` transaction
- If the notification service is down, events accumulate and drain when it recovers, in order
- Duplicate delivery (crash-after-mark) is prevented by the `notifications` PK

---

## Decision 4: SQLite WAL for the Persistent Layer (not PostgreSQL)

**Chosen for hackathon demo:** SQLite with WAL + `busy_timeout=5000`. Both instances share one file (same host).

**Production path:** `infra/001_init.sql` provides a full PostgreSQL schema with partial unique index on `assignment_groups` for multi-host deployment.

**Rationale:** Zero-setup for demo. SQLite WAL supports concurrent readers + one writer with 5 s busy timeout. All invariants (double assignment, partial batch) are enforced identically.

---

## Decision 5: Stateless App Instances with Client-Side Failover

**Chosen:** Two stateless Node.js instances behind HAProxy. WebSocket clients rotate endpoints on close (exponential backoff with jitter, max 3 s).

**Rationale:**
- No shared in-process state: Redis is the coordination bus
- If one instance dies, its subscribers reconnect to the other within 5 s (measured as `reconnect_ms` metric)
- HAProxy health checks (GET /api/health) remove failed instances in < 2 health periods (3 s each)

---

## Decision 6: Canvas-Based Maps (no tile library)

**Chosen:** HTML5 Canvas with custom Web Mercator projection. Dot rendering for 2,000 riders.

**Rationale:** No external library dependency. 2,000 dots at 60 fps is trivial for Canvas. Smooth rider-marker animation via `RiderMarker.tick()` interpolation. The operations map only redraws on dirty flag.

---

## Consequence Summary

| Property | Value |
|----------|-------|
| Map update latency p95 | < 500 ms (target < 2,000 ms) |
| Polling requests | 0 (HTTP 426 on GET /api/track/*) |
| DB location writes/s | ≈ 22/s for 2,000 riders (target < 50/s) |
| Nearest-rider search p95 | < 1 ms with miniredis, < 5 ms with real Redis |
| Double assignments | 0 (enforced by claim.lua atomicity) |
| Partial batch assignments | 0 (both orders claimed or neither) |
| Notification duplicates | 0 (idempotent outbox PK) |
| Client failover | < 5 s (3 s max reconnect delay) |
| Redis interruption | Fail-closed on assignment; auto-recover via rebuild() |
